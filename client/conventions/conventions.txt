FRONTEND CONVENTIONS — task-app client

These are guidelines, not law. They exist for one reason: so that adding the
next feature is copying an existing shape, never inventing a new one. That is
the whole test for whether a rule belongs here — does it make the code scale?
If a rule ever stops being true of the code, DELETE it or amend it; a
convention that lies is worse than no convention (the previous version of this
file outlived the data model it described and had to be torn out). Read this
alongside pattern.md (how the code is wired, both sides of the HTTP barrier)
and app_info.md (what the app is for the user).


0. THE THROUGH-LINE
   One symmetric pattern, repeated. Two resources (themes, items), four CRUD
   verbs each, both sides of the barrier — all share one skeleton. Deviations
   must be justified out loud, never improvised. Everything below is a specific
   application of this.


1. EXPORTS & BARRELS
   Named exports only, everywhere — no `export default`. Every folder that
   groups related files gets an index.js barrel re-exporting its public surface
   (`export { Board } from './Board'`). Consistent import style everywhere, and
   renaming a file never silently breaks an anonymous default import.


2. LAYERS, AND WHO MAY DEPEND ON WHOM
   Dependencies flow one direction only, down this list:

       components/  hooks/  api/     <- shared trifecta: the bottom layer,
             \        |       /          knows nothing of each other or of
              \       |      /           anything above. "Could this file be
               v      v     v            copied into an unrelated project and
              features/<name>/           still make sense?" If yes it lives
                     v                    here and must not know what a "theme"
                  pages/                  or "item" is.
                     v
                  layouts/  (parallel to pages/, depends only on components/)
                     v
                  routes/               <- wires URL -> (layout, page)
                     v
                  App.jsx               <- mounts router + app-wide providers
                     v
                  main.jsx              <- mounts App into the DOM

   features/ may import the trifecta. pages/ compose one-or-more features and
   nothing more — no fetching, no domain logic of their own (BoardPage is one
   line). A lower layer never imports a higher one.

   "Everything shared among features" IS the bottom trifecta. The test for
   belonging there is the copy-into-another-project one above — GENERIC-ness, not
   headcount. A piece that knows nothing of themes or items goes in the trifecta
   as soon as it exists, even if exactly one feature uses it today; that is where
   a reader looks for reusables, so a generic component hiding inside a feature
   folder is just a reusable nobody can find. What stays private to a feature is
   what KNOWS THE DOMAIN (a card that reads item.itemType, a column that renders a
   theme) — those never move up, however many callers they get.


3. api/ vs hooks/ — TWO UNRELATED AXES
   api/   is the only place allowed to know the server contract: URLs, methods,
          request/response shapes. Plain async functions that mirror the routes
          1:1 (getThemes, createItem, ...). request() is their single sink; see
          pattern.md. To add an endpoint, add one thin function here.
   hooks/ is generic React state orchestration around ANY async function. It
          never knows a URL or a resource. It grows along a different axis than
          api/: not by resource, but by LIFECYCLE SHAPE (section 4).


4. hooks/ IS ORGANIZED BY LIFECYCLE SHAPE, NOT BY VERB
   There are three hooks and there is a reason for each; do not add a fourth
   that only renames one of them (no usePatch/useDelete — they would be
   useMutation with a different label, duplicating every future fix N times).

     useQuery(asyncFn, deps)   The generic READ. Runs asyncFn on mount and when
                               deps change. Returns { data, setData, loading,
                               error }. Has NO opinion about what data is — a
                               number, an object, a list. Use it directly when
                               the data is not an _id-keyed list, or you need a
                               bespoke local update via raw setData.

     useMutation(asyncFn)      The generic WRITE. Runs only when you call
                               mutate(...args). Tracks its own loading. Returns
                               the result, or null on failure (failures go to
                               the notifications sink, section 8 — callers never
                               try/catch). The HTTP verb lives inside the api
                               function you pass; the hook neither knows nor
                               cares, so it is equally correct for create,
                               update, and delete.

     useCollection(fetchFn, deps)  A SPECIALIZATION of useQuery for the common
                               case: the fetched data is a list of documents
                               each with _id, kept in sync with the server
                               LOCALLY (no refetch after a write). It hides raw
                               setData and exposes the only two cache operations
                               the app ever needs — upsert(doc) (create OR
                               update) and remove(doc). It literally contains
                               useQuery; that is the relationship to understand.

   useQuery + useMutation are the read/write pair (the useQuery/useMutation
   vocabulary of React Query & SWR). useCollection is not a fourth verb — it is
   useQuery plus the two canonical cache ops, factored out so no feature rewrites
   them.

   Known friction: useQuery sets loading synchronously in its effect, which the
   react-hooks/set-state-in-effect rule flags. For a fetch-on-mount read hook
   that cascade (loading render -> data render) is the intended behavior, so the
   rule is suppressed on that one line by design — not worked around elsewhere.


5. THE CACHE INVARIANT (replaces the old "writes return the parent" rule)
   Every server write returns the affected TOP-LEVEL resource as JSON, keyed by
   _id — never 204/empty, never a parent wrapping it. Items are their own
   top-level documents now (see the models); an item write returns that item,
   not its theme.

   Therefore the client cache is a set of FLAT collections, each keyed by _id,
   each with exactly two operations: upsert and remove — which is precisely what
   useCollection provides. A single change is a single document: upsert swaps
   one entry and every other entry keeps its object identity. This is the fix
   for the old model, where tasks were embedded and any one task's change forced
   the whole parent list to be replaced. Never reintroduce a write that returns
   a container instead of the thing that changed.

   Mirror server side effects in the cache. Deleting a theme cascade-deletes its
   items on the server; the client must remove those items from the item cache
   too (ThemeColumn already holds them, so it loops remove over them after
   removing the theme) — otherwise the cache holds orphans.


6. ONE COORDINATOR PER FEATURE
   Each features/<name>/ has one component named after the folder (Board.jsx),
   the folder's ONLY public export from index.js. Everything else is private,
   reachable only by relative import from inside the folder.

   The coordinator is the only file allowed to know all of its direct children
   at once. It owns the shared data (Board runs the two useCollection calls) and
   hands each child its own slice as ordinary props. Children never import each
   other, so any one is replaceable without rippling into its siblings. This
   shape repeats at every layer: App coordinates providers+router; routes
   coordinate (layout, page); a page coordinates features; a feature coordinates
   its leaves.


7. SCOPED CONTEXT CARRIES CROSS-CUTTING CALLBACKS ONLY
   When a value must reach a descendant through an intermediate that doesn't
   care about it (an item's cache op must reach ItemCard through ThemeColumn),
   use a Context scoped to that one feature folder (BoardContext), created by
   the coordinator — not global state, not a prop threaded through indifferent
   levels.

   Shape it narrowly. Context carries only the "this write succeeded, update
   shared data" callbacks — here the four useCollection ops (upsertTheme,
   removeTheme, upsertItem, removeItem). It never carries the mutation itself
   and never the raw fetched data. Each leaf still owns its OWN useMutation and
   its OWN loading (so it shows its own pending state) and only reaches into
   context AFTER its write succeeds. Item-specific data (which theme a column
   is) still flows down as normal props via the render that iterates it.

   File split: a stateful Provider component and its context/hook go in separate
   files (react-refresh forbids a file exporting both components and non-
   components). BoardContext.js dodges this only because it re-exports a raw
   Context.Provider rather than defining a Provider component.


8. ERRORS CONVERGE TO ONE APP-WIDE SINK
   Two kinds, handled differently on purpose:
     - READ-load failure (useQuery/useCollection): the view has no data, so it
       renders an inline message where the data would be (Board's "Error: ...").
     - WRITE failure (useMutation): the view still has its data; the failure is
       transient. These converge to ONE global sink and surface as a toast.
   The convergence point is useMutation's own catch block, not each handler —
   every write already flows through it, so a new feature gets error reporting
   for free and cannot forget to wire it. This is why useMutation exposes no
   `error`: there is nothing for a component to display. The sink is app-level
   (notifications/, mounted in App.jsx above the router), generic like routing.


9. POLYMORPHISM: ONE EXPLICIT CARD PER itemType (features/board/ItemCards/)
   Items are one collection split by a discriminator (itemType: Task/Event/
   Reminder). The frontend mirrors that with ONE self-contained card component
   per type — TaskCard, EventCard, ReminderCard, each its own file in ItemCards/.
   No shared shell, no registry of slots. Each card writes the SAME base
   explicitly: the h-full card box, the universal top line (title EditableText +
   rename + delete), then its own body (Task's completed toggle, Event's two
   datetime inputs, Reminder's one). ThemeColumn dispatches per item with a small
   map { Task: TaskCard, Event: EventCard, Reminder: ReminderCard } and renders
   the match.

   This deliberately trades DRY for readability. The previous single ItemCard +
   registry ({ Details } slots) split the base and the type body across a shell
   and a lookup, so understanding one card meant reading three places. Three
   self-contained cards each read top-to-bottom as one whole thing; the cost is
   the near-identical base is written three times, and a base change touches all
   three — accepted on purpose.

   The line that trade stops at: a CARD SHELL is duplicated, a LEAF INPUT is not.
   The shell has no invariant to get wrong, so three copies cost nothing but
   keystrokes. An input with subtle correctness is the opposite — three copies are
   three places to get it wrong — so it becomes one generic primitive in
   components/ (§11). The datetime box every card needs is components/DateTimeField;
   the cards import it from the trifecta like any other component.

   Creation lives with CreateItem: it owns its own type list (the <select>
   options) and per-type creation defaults (Event seeds timeStart/timeEnd,
   Reminder seeds reminderTime=now, Task none) so a title-only create validates.

   Adding a fourth type: one new self-contained card in ItemCards/ (+ its barrel
   line), one entry in ThemeColumn's map, one entry in CreateItem's list/defaults.


10. GENERIC COMPONENTS STAY DUMB ABOUT DOMAIN — BUT MAY BE LAYOUT-CONFIGURABLE
    components/ files may never know what a theme or item is; that line is
    absolute. Layout is softer: a generic component may own a container as long
    as the container is driven by ABSTRACT, caller-supplied options, not baked-in
    assumptions.
    List is the example — a GRID, exposed as a symmetric transpose:
      flow     ('x'|'y')  the axis items fill, and which axis grows on overflow.
      slots    (count)    how many tracks on the FIXED cross axis.
      autoSize (a size)   the size of each track the grid IMPROVISES on overflow.
    flow='x' => columns are fixed (slots), rows are improvised (autoSize);
    flow='y' is the transpose. Swap x<->y and every column/row swaps with it.

    Static vs dynamic is the rule that shapes it: Tailwind reads your source as
    TEXT at build time and emits CSS only for complete class literals it finds.
    `flow` has two known outcomes, so it stays a class via a literal map
    ({ x:'grid-flow-row', y:'grid-flow-col' }). `slots` and `autoSize` are open
    values assembled at runtime — Tailwind would never see `grid-cols-${n}`, so
    they go through inline `style` (gridTemplateColumns/Rows, gridAutoRows/
    Columns). Rule: a fixed, known set of values -> class; an open value -> style.

    Track-size lesson: a grid's improvised tracks default to `auto` and, in a
    definite-height container, are STRETCHED equally to fill it — which is why N
    rows each become 1/N tall. Give autoSize a definite `100%` to make each
    improvised row full-height and let the rest overflow (the container needs a
    definite height, e.g. h-full, for the % to resolve). For a scrolling list
    that keeps natural item heights, use `min-content` and bound the list itself
    with flex-1 min-h-0 overflow so it scrolls instead of growing its parent.
    To show exactly N tracks before the rest scrolls, size each gap-aware:
    autoSize = calc((100% - (N-1)*gap) / N) — e.g. 3 cards at gap-4 is
    calc((100% - 2rem) / 3); plain 100/N% ignores the gaps and clips the last.


11. ONE INPUT PRIMITIVE PER KIND OF VALUE
    There are exactly two, and the split is by the KIND OF VALUE being edited, not
    by which screen edits it: EditableText for text, DateTimeField for a datetime.
    Both live in components/ and both COMMIT THE SAME WAY — on Enter or blur, from
    an uncontrolled input, so a rejected write leaves the user's typing on screen.
    Learn the contract once and it holds for both.

    DateTimeField wraps a native <input type="datetime-local"> and exists to hold
    two non-obvious rules that were being got wrong per-copy:
      - it is NEVER `disabled` while its write is in flight. Disabling a focused
        input BLURS it, which throws the user out of the field after they type a
        single segment.
      - it NEVER writes on change. A datetime-local fires change as soon as its
        value parses, i.e. mid-typing, so one edit became a burst of PATCHes.
    Its focused-segment highlight cannot be reached by any utility (the segments
    are browser pseudo-elements), so that one rule lives in index.css keyed off a
    plain `.datetime-field` class — the documented exception to PAINT-in-`styles`.

    The rest of this section is EditableText (rename AND live-create):
    EditableText is the single controlled-text primitive; there is no separate
    TextInput anymore. Inactive it renders <span>{value}</span>; active it
    renders a BARE <input> — no <form>, no submit button — so the caller styles
    and sizes the box directly via inputClassName (flex-1 in a header row, w-full
    in a draft). Enter or blur commits (onSubmit(currentValue)); Escape cancels
    (onCancel). It is uncontrolled (defaultValue + a ref), so it re-seeds from the
    current value every time it goes active and needs no manual reset.

    The parent owns `active` and decides what commit/cancel MEAN — that is what
    lets one primitive serve two jobs:
      - RENAME an existing element: parent holds a `renaming` flag, flips it off
        on success (input unmounts -> span shows the new value), leaves it on for
        a server failure (the uncontrolled input keeps the user's text). An empty
        submit is treated as cancel by the parent's handler.
      - LIVE-CREATE: the parent renders a draft element (a column/card that looks
        like the real thing) holding an EditableText that is always `active` with
        value="". Submit persists + upserts + unmounts the draft; cancel (Escape,
        or blur while empty) just unmounts it, so it "disappears." autoFocus on
        mount is the flashing cursor.

    A create is therefore a draft element wearing an active EditableText, not a
    distinct always-present field — which is exactly why the old two TEXT
    primitives collapsed into one. Don't add a third text input; if a caller needs
    a different box, that is what inputClassName is for. A new primitive is earned
    only by a new KIND of value (a duration, a colour beyond ColorPicker), never by
    a new caller wanting a different-looking box.


12. NAMING THAT FLOWS FROM THE ABOVE
    - api function: <verb><Resource> mirroring the route (createItem).
    - the mutation trigger from a hook is aliased <operation>Mutation
      (const { mutate: deleteThemeMutation } = useMutation(deleteTheme)).
    - a leaf's handler wrapping that trigger is named by the UI interaction:
        field-backed op (a text field, two outcomes): submit<X> / cancel<X>
          (submitRenameTheme, cancelRenameTheme).
        click-once command (one button, no cancel): run<X> (runDeleteTheme,
          runToggleCompleted).
    - the coordinator's cache callbacks are the useCollection ops themselves,
      named upsert<Resource> / remove<Resource>. (The old handle<X> cache
      callbacks are gone — useCollection replaced the hand-written triplet.)


13. CLASSNAME OWNERSHIP — ONE AXIS PER LAYER
    layouts/  own viewport occupancy + chrome positioning: h-screen, overflow,
              fixed relative to the viewport. Never reach inside the Outlet.
    pages/    own spacing BETWEEN sibling features on a screen. Never touch
              viewport height/scroll, never a feature's internal layout.
    features/ own everything about how their own content presents: columns, card
              sizing, internal spacing. Must stay layout-agnostic — no h-screen,
              no fixed, no assumption about container size; size relative to the
              parent (w-full, etc.). `sticky` is allowed inside a feature
              (pins to whatever the scrolling ancestor is); `fixed` is not (it
              assumes the viewport — a layout concern).
    Test: "would this className still make sense if I swapped what's on the other
    side of the boundary?"


14. SPACING HAS NAMED ROLES — REUSE, DON'T RE-GUESS
    Tailwind's scale is already consistent; the mess comes from picking a fresh
    number per edit. Pick a ROLE and reuse its number everywhere:
      4  = tight internal grouping (padding inside a card/column, gaps between
           elements of one unit, and small fixed controls like an h-4 w-4 button
           — deliberately the same 4 so control size and its spacing read as one
           scale).
      10 = section/page-level separation (a feature's padding against its
           container edge, p-10 on the board).
    Before writing a new spacing class, ask "tight grouping or section
    separation?" and reuse 4 or 10. If a genuinely new situation fits neither,
    NAME a third role here — don't invent a silent one-off. Anything meant to
    grow gets a min-h-* floor with flex-1, never a fixed h-* that caps it.


15. COLOUR HAS NAMED ROLES TOO
    The aesthetic pass has happened: the old placeholder slate palette is gone,
    replaced by the named tokens in index.css @theme (shared with the hub, so the
    two sites read as one domain). Same discipline as spacing — reuse a token for
    a ROLE, never pick a new one per component. Tokens, by role:

      surfaces, darkest -> lifted as you come forward:
        void      the page ground, and any input WELL sunk into a surface
                  (a datetime field, the agent's prompt box).
        obsidian  chrome and side panels — navbar, agent panel, ThemeRows,
                  a board theme column.
        crypt     the things you act on: item cards, a theme's header row,
                  the ColorPicker popover, a confirm box.
        border    every hairline. Halve it (border-border/40, /70) where a rule
                  should recede rather than divide.
      text, brightest -> faintest:
        parchment      primary content (a title, a value).
        parchment-dim  labels and secondary lines; also a resting icon button.
        ash            tertiary and OFF states — an idle toggle, a hint, a
                       struck-through completed title.
      accents — azure leads, violet and teal support:
        accent         the primary "this one is live" mark: the active nav star,
                       a focused field's border, a completed task.
        accent-bright  the hover partner for any accent or dim element.
        accent-violet  Reminder's identity, and a theme's visible toggle.
        accent-teal    Event's identity, and a task's deadline toggle.
        danger         destructive only — delete, and read-load error text.

    ON/OFF pairs state BOTH halves and differ by more than colour where the
    distinction matters: a completed task swaps its GLYPH (faCheck -> faSquareCheck)
    and strikes its title, not just recolours, because a colour-only change is
    invisible at a glance across a full board.

    A live-create draft reuses its real element's surface (a draft card crypt) so
    the half-made element looks like the thing it is becoming.

    Known unused: --color-elevated is defined in @theme but referenced nowhere.
    Either give it a role above or delete it; don't leave it as a fourth surface
    that nothing explains.
