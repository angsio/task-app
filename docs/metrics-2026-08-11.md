Sources: `npm run eval` then `npm run metrics -- --kind eval`, in `server/`.
Correctness figures from `npm run txcheck`. Record sizes measured from a real

LLM scheduling agent. Node/Express + React + MongoDB Atlas, self-hosted on a
Raspberry Pi 4B behind nginx and a Cloudflare tunnel. Live at
tasks.frangiclave.com.

## How the agent works

The model starts a turn holding one tool: `find_tools`. It describes the
capability it needs in plain words, that description is embedded, and the
nearest tools by cosine similarity in a pgvector index are returned and made
callable. The number of tools in the prompt does not grow with the catalogue.

| | |
|---|---|
| Tools total | 9 |
| Retrievable by search | 8 |
| Requiring user confirmation before executing | 6 |
| Read-only, execute immediately | 2 |
| Tools returned per search | 3 |
| Similarity threshold to return anything | 0.13 |
| Max model round trips per turn | 8 |

Every write is gated: the turn returns to the browser with a pending action and
executes nothing until the user answers. Ownership comes from the session, never
the request body. Gated and once-only calls route through a MongoDB ledger with
a unique index on `(owner, callId)`, so a resent call replays its first outcome
instead of running twice.

An approved set of calls runs inside a single MongoDB transaction, ordered so a
theme is written before the items filed under it and deleted after them. The
first error rolls back every write in the set, and the ledger forgets those
calls so a retry runs them rather than replaying a failure.

## Retrieval accuracy per tool

46 test queries run against the real embedding model and the real pgvector
index. 40 name a correct tool; production returns the top 3.

| tool | cases | correct at rank 1 | correct in top 3 | worst rank |
|---|---|---|---|---|
| create_items | 7 | 85.7% | 100.0% | 2 |
| create_themes | 3 | 100.0% | 100.0% | 1 |
| delete_items | 5 | 100.0% | 100.0% | 1 |
| delete_themes | 3 | 100.0% | 100.0% | 1 |
| list_items | 8 | 75.0% | 100.0% | 2 |
| list_themes | 5 | 60.0% | 80.0% | 4 |
| update_items | 6 | 66.7% | 100.0% | 3 |
| update_themes | 5 | 100.0% | 100.0% | 1 |

Overall, across all 40:

| k | correct tool in top k | recall@k | precision@k |
|---|---|---|---|
| 1 | 87.5% | 0.850 | 0.875 |
| 2 | 97.5% | 0.963 | 0.500 |
| 3 | 100.0% | 0.988 | 0.342 |
| 5 | 100.0% | 1.000 | 0.210 |

MRR 0.933. Nothing goes unretrieved at any k. Retrieval latency p50 517 ms,
p95 748 ms.

Hit rate reaches 100% at k=3 while recall@3 is 0.988, because one case names two
tools and only one of them lands in the top 3. That case is the whole of the
`list_themes` shortfall in the table above.

precision@k is capped at |expected| / k, so with one correct tool per case it
cannot exceed 1/k. The falling column is arithmetic, not degradation.

## What the eval located

An earlier run missed one case at k=3:

```
query     file an existing item under a different theme
wanted    update_items
got       update_themes 0.481   create_themes 0.434   list_themes 0.343
```

The cause was in the tool descriptions, not the retrieval. Each write tool
carried a disclaimer pointing at its counterpart — the theme tools said "never
the items inside it" and "use the tool that updates items". Embeddings have no
representation of negation, so naming items inside a theme tool moves it toward
item queries rather than away. Removing those clauses fixed the case.

Rewriting them exposed a second version of the same fault: three theme tools
given an identical definitional sentence became interchangeable and crowded out
`list_themes`, and item nouns left inside `list_themes` pulled it into item
queries. Descriptions now name only their own object.

Every in-catalogue case is now retrieved in the top 3. The eval located both
faults precisely; neither was visible from reading the code.

## Threshold calibration

The similarity threshold was 0.05, where it rejected nothing. Four test queries
from unrelated domains (email, weather, translation, music) bounded it against
the correct matches:

| | similarity |
|---|---|
| Highest-scoring unrelated request | 0.1025 |
| Lowest-scoring correct match | 0.1692 |

A gap of 0.0667 with nothing inside it. Set to 0.13:

| | before (0.05) | after (0.13) |
|---|---|---|
| Unrelated requests rejected | 0 of 4 | 4 of 4 |
| Correct matches still retrieved | 40 of 40 | 40 of 40 |

Two further cases use scheduling vocabulary for capabilities that do not exist —
exporting a schedule (0.4180) and sharing a calendar (0.3342). Both outscore
most correct matches, so no threshold separates them without discarding valid
requests. Reading a schedule genuinely is half of what those ask for; the part
that is missing is the export, not the read. They are measured and excluded from
the rejection rate rather than counted as failures, and the refusal is handled
in the system prompt instead.

## Model configuration

`openai.gpt-oss-120b` on Bedrock, `amazon.titan-embed-text-v2` for embeddings.
Reasoning effort measured on one prompt, two runs each:

| setting | output tokens |
|---|---|
| gateway default | 2355, 2241 |
| low | 1037, 1021 |
| medium | 2558, 2436 |
| high | 3795, 3108 |

The gateway default is medium, so pinning it explicitly costs and saves nothing;
it stops the value drifting underneath the app. `low` roughly halves output
tokens but phrases its tool searches less precisely — asked to set a reminder it
searched for "create an event" — and that phrasing is the input to retrieval, so
it was not taken.

## Correctness suite

`npm run txcheck` runs 21 assertions against a real MongoDB replica set, on a
scratch database on the same cluster as the app, dropped afterwards. It covers
what unit tests cannot reach: that a tool sees an earlier tool's uncommitted
write inside the same transaction, that a failed set leaves nothing behind, that
the ledger forgets rolled-back calls, that a tool which throws still unwinds,
and that deleting a theme cascades to its items.

## Metrics subsystem

| | |
|---|---|
| Lines, whole subsystem | 903 |
| Event types | 5 |
| Emit points in the agent loop | 9 |
| External dependencies added | 0 |
| Storage | JSONL, one file per day, 30-day retention |

Events: `turn.start`, `model.call`, `tool.call`, `confirmation`, `turn.end`.

Written inline by the request that generates them — no daemon, no queue, no
database. Writes go to an already-open append stream, so no turn waits on I/O,
and a failing sink disables itself permanently rather than propagating into the
request path.

Record sizes, measured from a real turn:

| event | bytes |
|---|---|
| turn.start | 231 |
| model.call | 395 |
| tool.call | 247 |
| turn.end | 488 |

`confirmation` was not exercised in that turn. A turn costs
`231 + 395n + 247m + 488` for n model round trips and m tool calls: 1,361 bytes
for a one-step turn, 3,534 for the four-step turn measured here. At 100
four-step turns a day that is roughly 345 KB/day and 10 MB over a 30-day window.

No prompts, replies, item titles or theme names are written. Account IDs are
salted and hashed to 12 hex characters. Content logging exists behind an
explicit opt-in flag, off by default.

The chat model and the embedding model are billed separately and never summed:
the chat model has input and output tokens, the embedding model has input tokens
only, because a vector is not tokens. Token counts come from the provider when
reported and are labelled estimated when they are not.

## Not measured

No production telemetry exists yet. The subsystem is built, instrumented and
exercised, but the app has not served real traffic with it, so there are no
figures for cost per turn, completion rate, approval rate, or error rates from
use. Every number above comes from the offline evaluation, the correctness
suite, or direct measurement against a scratch database.
