# task-app — measured data, 2026-08-11

A snapshot, not a living document. Numbers come from the eval run recorded that
day and from the code as it stood; both move. Write a new dated file rather than
editing this one, so the history is readable.

Sources: `npm run eval` then `npm run metrics -- --kind eval`, in `server/`.

LLM scheduling agent. Node/Express + React + MongoDB Atlas, self-hosted on a
Raspberry Pi 4B behind nginx and a Cloudflare tunnel. Live at
tasks.frangiclave.com.

## How the agent works

The model starts a turn holding one tool: `find_tools`. It describes the
capability it needs in plain words, that description is embedded, and the
nearest tools by cosine similarity in a pgvector index are returned and made
callable. The number of tools in the prompt does not grow with the catalogue.

| | |
|---|---|
| Tools total | 9 |
| Retrievable by search | 8 |
| Requiring user confirmation before executing | 6 |
| Read-only, execute immediately | 2 |
| Tools returned per search | 3 |
| Similarity threshold to return anything | 0.13 |
| Max model round trips per turn | 8 |

Every write is gated: the turn returns to the browser with a pending action and
executes nothing until the user answers. Ownership comes from the session, never
the request body. Gated and once-only calls route through a MongoDB ledger with
a unique index on `(owner, callId)`, so a resent call replays its first outcome
instead of running twice.

## Retrieval accuracy per tool

46 test queries run against the real embedding model and the real pgvector
index. 40 name a correct tool; production returns the top 3.

| tool | cases | correct at rank 1 | correct in top 3 | worst rank |
|---|---|---|---|---|
| create_items | 7 | 71.4% | 100.0% | 2 |
| create_themes | 3 | 100.0% | 100.0% | 1 |
| delete_items | 5 | 100.0% | 100.0% | 1 |
| delete_themes | 3 | 100.0% | 100.0% | 1 |
| list_items | 8 | 75.0% | 100.0% | 2 |
| list_themes | 5 | 60.0% | 80.0% | 5 |
| update_items | 6 | 66.7% | 83.3% | 4 |
| update_themes | 5 | 80.0% | 100.0% | 2 |

Overall, across all 40:

| k | correct tool in top k | recall@k | precision@k |
|---|---|---|---|
| 1 | 82.5% | 0.813 | 0.825 |
| 2 | 95.0% | 0.938 | 0.487 |
| 3 | 97.5% | 0.963 | 0.333 |
| 5 | 100.0% | 1.000 | 0.210 |

MRR 0.902. Every case is retrieved by k=5. Retrieval latency p50 540 ms,
p95 778 ms.

precision@k is capped at |expected| / k, so with one correct tool per case it
cannot exceed 1/k. The falling column is arithmetic, not degradation.

## The one failure, and what it says

One case of 40 misses at k=3:

```
query     file an existing item under a different theme
wanted    update_items
got       update_themes 0.481   create_themes 0.434   list_themes 0.343
```

The word "theme" dominates the embedding even though the item is what changes,
so all three theme tools outrank the item tool. This is a tool-description
problem the eval located precisely, not a limit of the approach.

## Threshold calibration

The similarity threshold was 0.05, where it rejected nothing. Four test queries
from unrelated domains (email, weather, translation, music) bounded it against
the correct matches:

| | similarity |
|---|---|
| Highest-scoring unrelated request | 0.1025 |
| Lowest-scoring correct match | 0.1692 |

Nothing falls between. Set to 0.13:

| | before (0.05) | after (0.13) |
|---|---|---|
| Unrelated requests rejected | 0 of 4 | 4 of 4 |
| Correct matches still retrieved | 40 of 40 | 40 of 40 |

Two further cases use scheduling vocabulary for capabilities that do not exist —
exporting a schedule (0.4180) and sharing a calendar (0.3342). Both outscore
most correct matches, so no threshold separates them without discarding valid
requests. They are measured and excluded from the rejection rate rather than
counted as failures.

## Metrics subsystem

| | |
|---|---|
| Lines, whole subsystem | 853 |
| Event types | 5 |
| Instrumentation points in the agent loop | 8 |
| External dependencies added | 0 |
| Storage | JSONL, one file per day, 30-day retention |

Events: `turn.start`, `model.call`, `tool.call`, `confirmation`, `turn.end`.

Written inline by the request that generates them — no daemon, no queue, no
database. Writes go to an already-open append stream, so no turn waits on I/O,
and a failing sink disables itself permanently rather than propagating into the
request path.

Record sizes, measured:

| event | bytes |
|---|---|
| turn.start | 230 |
| model.call | 374 |
| tool.call | 354 |
| turn.end | 490 |
| one full turn | ~1,822 |

At 100 turns/day, ~178 KB/day and ~5.2 MB over a 30-day window.

No prompts, replies, item titles or theme names are written. Account IDs are
salted and hashed to 12 hex characters. Content logging exists behind an
explicit opt-in flag, off by default.

The chat model and the embedding model are billed separately and never summed:
the chat model has input and output tokens, the embedding model has input tokens
only, because a vector is not tokens. Token counts come from the provider when
reported and are labelled estimated when they are not.

## Not measured

No runtime telemetry exists yet. The subsystem is built and tested but the app
has not been deployed with it, so there are no production figures for latency,
cost per turn, completion rate, approval rate, or error rates. Every number
above comes from the offline evaluation or from reading the code.
